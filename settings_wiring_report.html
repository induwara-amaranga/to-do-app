Tier 2
Needed new logic, not just a missing parameter

These required understanding a platform constraint or a pre-existing design gap before any code could be written.

Date & time display formatdateFormat, timeFormat
wired
beforeSix call sites each hardcoded their own DateFormat('MMM d, yyyy h:mm a')-style pattern.
→
afterOne set of display helpers, all reading the two format settings.
The trap here: DateTimeUtilsHelper.formatDate / formatTime are also the functions used to write dates into storage (always yyyy-MM-dd / HH:mm, regardless of what the user prefers to look at). Changing their default behavior would have quietly corrupted every task's stored due date. So the fix is additive: five new display-only functions (displayDateNumeric, displayDateFriendly, displayMonthYear, displayDayMonth, displayTime), and a pass through every screen that shows a date to a human, swapping the hardcoded pattern for the matching helper — while leaving every storage-format parse call (e.g. filtered-tasks reconstructing a DateTime from a saved row) untouched.

Notification & alarm ringtonenotifRingtone, alarmRingtone
wired
beforeRingtone picker (native, Kotlin side) worked and stored a real content:// URI. Nothing read it.
→
afterReminders actually play the picked tone.
Android notification channels are immutable once created — a channel's sound can't be changed after the fact, only replaced by a new channel. So the channel id is now derived from a hash of the ringtone URI: pick a different tone and the app quietly creates a fresh channel instead of silently keeping the old sound forever. Full-screen (high-priority, "alarm-like") reminders use alarmRingtone; everything else uses notifRingtone — the app has no separate real alarm-scheduling path, so that's the only meaningful place the two settings can diverge. Low-priority reminders are silent by design (playSound: false) and were left alone.
services/notification_service.dart
Time zonetimeZoneLabel
wired — bug fix
beforePicking a time zone in Settings had zero effect.
→
afterA manual pick sticks across restarts.
main.dart's initLocalTimeZone() auto-detects the device zone and overwrites settings.timeZoneLabel on every launch — so any manual choice was silently reverted a moment later. Added a timeZoneManuallySet flag that tells startup to skip auto-detection. That surfaced a second gap: the picker shows friendly labels like "UTC+5:30 (Colombo / Mumbai)", but the timezone engine needs a real IANA id like "Asia/Colombo" — so a label→IANA lookup table was needed before "respect the manual choice" could mean anything. Picking a zone now also applies immediately, not just on next launch.

Morning plan · Evening review · Task overviewmorningPlan, eveningReview, taskOverview
wired — new
beforeThree toggles in Settings. No scheduling code existed for any of them, at all.
→
afterThree daily repeating notifications, one per toggle.
Each toggle now schedules (or cancels) a daily notification at a fixed time — 7:30am, 9:00pm, and noon respectively, since no time-picker exists yet for any of them. Fixed notification IDs (900001–900003) make rescheduling idempotent: flipping a toggle replaces that one notification rather than piling up duplicates. Wired to run once at app startup and again immediately whenever a Notifications setting changes, so toggling takes effect without a restart.
